# Requirements Document

## Introduction

This spec covers a cleanup and refactoring of the database setup files, migration module, and CI workflows in the `capuchin` project. The goal is to reduce duplication, remove noise, and make the codebase easier to maintain — without changing any existing runtime behaviour or architectural philosophy.

Areas in scope:
- `backend/db/init.sql` and `backend/migration/db/init.sql` (intentionally separate files serving different purposes)
- `backend/migration/` (go.mod version inconsistency, test-only direct dependencies)
- `.github/workflows/` (duplicated job logic, invalid expression syntax, placeholder noise)

## Glossary

- **Init_SQL**: `backend/db/init.sql` — the single canonical auto-generated schema snapshot. Serves a dual purpose: used by Docker Compose to bootstrap a fresh local dev database container, and referenced by migration integration tests (e.g. `TestInitSQLMatchesMigrationEndState`) as the schema reference. Regenerated by CI after each successful migration run. Must not be edited manually.
- **Migration_Module**: The standalone Go module at `backend/migration/` responsible for running goose migrations.
- **CI_Workflow**: A GitHub Actions YAML file under `.github/workflows/`.
- **Reusable_Workflow**: A GitHub Actions workflow callable from other workflows via `workflow_call`, used to deduplicate shared job logic.
- **Regenerate_Job**: The job that runs `pg_dump`, prepends a header, and commits `backend/db/init.sql` back to the repository. Currently duplicated verbatim in `release.yml` and `migrate-manual.yml`.
- **Port_Expression**: The GitHub Actions expression `${{ secrets.POSTGRES_PORT != '' && secrets.POSTGRES_PORT || '5432' }}` — JavaScript ternary syntax that is not valid in `env:` blocks and must be removed.

## Requirements

### Requirement 1: Consolidate the Regenerate-Init-SQL CI Job

**User Story:** As a developer, I want the `regenerate-init-sql` job to exist in exactly one place, so that any future changes to it only need to be made once.

#### Acceptance Criteria

1. THE CI_Workflow system SHALL extract the `regenerate-init-sql` job into a single reusable workflow file (e.g. `.github/workflows/regenerate-init-sql.yml`) callable via `workflow_call`.
2. WHEN `release.yml` needs to regenerate `init.sql`, THE CI_Workflow system SHALL call the Reusable_Workflow instead of defining the job inline.
3. WHEN `migrate-manual.yml` needs to regenerate `init.sql`, THE CI_Workflow system SHALL call the Reusable_Workflow instead of defining the job inline.
4. THE Reusable_Workflow SHALL accept the environment name as an input so the commit message can remain environment-specific.
5. AFTER the refactor, THE CI_Workflow system SHALL produce identical observable behaviour to the current inline job (same `pg_dump` flags, same header, same git commit message pattern).

---

### Requirement 2: Remove Invalid Port Expressions and Require Secrets-Only Port Configuration

**User Story:** As a developer, I want all DB connection values in CI to come exclusively from GitHub Actions secrets, so that no port or connection detail is ever silently hardcoded in a workflow file.

#### Acceptance Criteria

1. THE CI_Workflow system SHALL replace every occurrence of `${{ secrets.POSTGRES_PORT != '' && secrets.POSTGRES_PORT || '5432' }}` with `${{ secrets.POSTGRES_PORT }}` — with no fallback value.
2. THE CI_Workflow system SHALL apply this fix in all workflow files where the pattern appears (`release.yml` and `migrate-manual.yml`).
3. IF `POSTGRES_PORT` is not configured as a GitHub Actions secret, THE CI_Workflow system SHALL fail the workflow step rather than silently defaulting to any port value.
4. WHEN `POSTGRES_PORT` is set as a GitHub Actions secret, THE CI_Workflow system SHALL use that value for all DB connection steps in the workflow.
5. THE CI_Workflow system SHALL contain no hardcoded port numbers (e.g. `5432`) anywhere in any workflow file.

---

### Requirement 3: Remove Placeholder Noise from release.yml

**User Story:** As a developer, I want `release.yml` to contain only actionable steps, so that the file is easy to scan and doesn't mislead contributors.

#### Acceptance Criteria

1. THE CI_Workflow system SHALL remove all commented-out example deployment steps from the `deploy` job in `release.yml` (the SSH deploy example, the registry push example, and their associated inline comments).
2. THE CI_Workflow system SHALL retain the `Deployment placeholder` step (or a minimal equivalent) so the `deploy` job remains structurally valid and runnable.
3. THE CI_Workflow system SHALL retain the explanatory comment directing developers to replace the placeholder with their actual deployment mechanism.

---

### Requirement 4: Align Go Version in Migration Module

**User Story:** As a developer, I want all Go modules in the repository to declare the same Go toolchain version, so that builds are consistent and version drift is obvious.

#### Acceptance Criteria

1. THE Migration_Module `go.mod` SHALL declare `go 1.25.5`, matching the version declared in `backend/go.mod` (the single source of truth).
2. THE CI_Workflow system SHALL confirm that all `setup-go` steps across all workflow files already use `go-version: "1.25.5"` — no changes to CI are required for this requirement.
3. IF the `go.sum` file requires updating after the version bump, THE Migration_Module SHALL include the updated `go.sum`.

---

### Requirement 5: Move Test-Only Direct Dependencies to Correct Position in Migration go.mod

**User Story:** As a developer, I want `go.mod` to accurately reflect which dependencies are required by the production binary versus tests only, so that the module graph is honest and auditable.

#### Acceptance Criteria

1. THE Migration_Module `go.mod` SHALL NOT list `github.com/google/uuid` as a direct (non-indirect) dependency, because it is only imported in test files (`migrate_test.go`).
2. THE Migration_Module `go.mod` SHALL NOT list `golang.org/x/crypto` as a direct (non-indirect) dependency, because it is only imported in test files (`migrate_test.go`).
3. WHEN `go mod tidy` is run in `backend/migration/`, THE Migration_Module `go.mod` SHALL produce no changes to the set of direct dependencies listed.
4. THE Migration_Module binary (`cmd/migrate/main.go`) SHALL continue to compile and run correctly after this change.

---

### Requirement 6: Unify init.sql into a Single Canonical File

**User Story:** As a developer, I want a single canonical `init.sql` at `backend/db/init.sql`, so there is no duplication and no confusion about which file is authoritative.

#### Acceptance Criteria

1. THE `backend/migration/db/init.sql` file SHALL be deleted.
2. THE `backend/db/init.sql` file SHALL be the single canonical schema snapshot, serving both purposes: Docker bootstrap AND migration test reference.
3. WHEN `TestInitSQLMatchesMigrationEndState` reads `init.sql`, THE test SHALL use `os.ReadFile("../../db/init.sql")` so it reads from the unified location at `backend/db/init.sql`.
4. AFTER this change, THE `TestInitSQLMatchesMigrationEndState` test SHALL continue to pass.
5. THE `backend/migration/db/embed.go` file SHALL NOT be modified — it only embeds `migrations/*.sql` and is unaffected by the removal of `init.sql`.
6. THE `backend/db/init.sql` file SHALL contain a header comment explaining: it is auto-generated by CI after each migration run, used by Docker for fresh DB bootstrap, and also referenced by migration integration tests.
7. AFTER this change, no other files in the Migration_Module SHALL reference `backend/migration/db/init.sql`.

---

### Requirement 7: Preserve All Existing Tests and Behaviour

**User Story:** As a developer, I want the cleanup to leave all existing tests passing and all runtime behaviour unchanged, so that the refactor introduces no regressions.

#### Acceptance Criteria

1. AFTER all cleanup changes are applied, THE `backend` module SHALL pass `go test ./...` with no failures.
2. AFTER all cleanup changes are applied, THE Migration_Module SHALL pass `go build ./...` and `go vet ./...` with no errors.
3. THE `TestInitSQLMatchesMigrationEndState` test SHALL continue to pass, confirming `backend/db/init.sql` remains structurally equivalent to the goose migration end state.
4. THE `TestDBHealthFlag_ReflectsConnectionState` test SHALL continue to pass.
5. IF any CI workflow file is modified, THE modified workflow SHALL remain syntactically valid YAML and pass GitHub Actions schema validation.
